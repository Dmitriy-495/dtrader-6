# Инструкция: настройка build-песочницы Claude для сборки/проверки Go-кода

Эта инструкция — для Клода в чате analyzer (и для любого следующего
сервиса dtrader-6). Написана братом-Клодом из чата market-data, по
итогам реальной, методом проб и ошибок настроенной песочницы.

## Зачем это нужно

По умолчанию в песочнице Claude **нет установленного Go**, а сетевой
доступ ограничен списком разрешённых доменов (обычно под PyPI/npm/
crates.io — то есть под Python/Node/Rust, не под Go). Без этой
настройки Клод может только **читать код глазами** и рассуждать о
нём, но не может реально запустить `go build`/`go vet` и поймать
настоящие ошибки компиляции до того, как их увидит человек.

С этой настройкой Клод может собирать, проверять и даже **живьём
запускать** Go-программы (см. пример в конце — там, где мы гоняли
`config.Load()` на двух тестовых конфигах и реально смотрели вывод).

## Шаг 1 — проверить, что реально доступно в сети песочницы

```bash
# Смотрим список разрешённых доменов — обычно указан в системном промпте
# в блоке <network_configuration>. Ищи archive.ubuntu.com/security.ubuntu.com
# (это значит можно ставить пакеты через apt) и github.com/codeload.github.com
# (значит можно клонировать репозитории и качать Go-модули напрямую с GitHub).
```

Если `archive.ubuntu.com` есть в списке — Go можно поставить через apt
(см. Шаг 2). Если нет — придётся искать другой путь (собрать из
исходников через git, что дольше и не гарантированно).

## Шаг 2 — установить Go через apt (не через go.dev!)

`go.dev`/`dl.google.com` почти наверняка НЕ в allowlist песочницы —
поэтому официальный дистрибутив Go оттуда не скачать. Но подходящая
версия почти всегда есть в стандартных репозиториях Ubuntu:

```bash
apt-cache search golang | grep golang-1.2   # посмотреть доступные версии
apt-get install -y golang-1.22-go            # ставим нужную (сверить с go.mod проекта)
```

После установки бинарник обычно лежит в `/usr/lib/go-1.22/bin/go` —
не в `PATH` по умолчанию. Прописываем симлинк:

```bash
ln -sf /usr/lib/go-1.22/bin/go /usr/local/bin/go
go version   # должно показать что-то вроде "go version go1.22.2 linux/amd64"
```

⚠️ Версия из apt почти наверняка будет отличаться от версии в `go.mod`
проекта в последней цифре (например, apt даёт `1.22.2`, а `go.mod`
требует `go 1.22.3`). Это нормально и решается на следующем шаге —
не нужно пытаться найти точную версию побитово.

## Шаг 3 — заставить Go использовать локальный тулчейн, а не докачивать нужную версию

Начиная с Go 1.21 команда `go build` при несовпадении версии в `go.mod`
пытается **автоматически скачать** нужный тулчейн с `proxy.golang.org` —
а этот домен тоже не в allowlist. Заставляем Go смириться с локальной
версией:

```bash
export GOTOOLCHAIN=local
```

Если версия в `go.mod` СТРОГО больше версии из apt (например требует
`1.22.3`, а стоит `1.22.2`) — `go build` откажется работать даже с
`GOTOOLCHAIN=local`, с ошибкой вида `go.mod requires go >= 1.22.3`.
В этом случае (см. пример в market-data) можно **в отдельной build-check
копии проекта**, не трогая оригинал, временно понизить версию в
`go.mod`:

```bash
sed -i 's/^go 1.22.3/go 1.22.2/' go.mod   # только в копии для проверки!
```

Это безопасно, потому что понижение версии в `go.mod` практически
никогда не меняет семантику компиляции для типового прикладного кода
(если только не используются самые новые фичи языка последней минорной
версии, что маловероятно).

## Шаг 4 — обойти module proxy (proxy.golang.org тоже не в allowlist)

По умолчанию `go build` качает внешние зависимости (все `require` в
`go.mod`) через `proxy.golang.org`. Переключаем на прямое скачивание
из git-репозиториев (что работает, раз `github.com`/`codeload.github.com`
разрешены):

```bash
export GOPROXY=direct
export GOSUMDB=off   # иначе Go попытается сверить чексуммы через sum.golang.org — тоже недоступен
```

Большинство модулей с путём вида `github.com/author/repo` после этого
скачаются нормально.

## Шаг 5 — модули с "vanity import path" (не начинаются на github.com)

Некоторые популярные модули используют красивый домен-редирект вместо
прямого `github.com/...` (например `go.yaml.in/yaml/v3`,
`go.uber.org/atomic`, `golang.org/x/...` и подобные). Такие домены
(`go.yaml.in`, `go.uber.org`, `golang.org`) почти наверняка НЕ в
allowlist — `GOPROXY=direct` тут не поможет, потому что сначала нужно
дойти до самого домена-редиректора, чтобы узнать, куда он ведёт.

Решение — найти настоящий GitHub-репозиторий модуля (обычно легко
гуглится: "\<module-path\> github mirror") и подключить его через
`replace` на локально склонированную копию:

```bash
mkdir -p /home/claude/vendor-src
cd /home/claude/vendor-src

git clone --depth 1 --branch v3 https://github.com/yaml/go-yaml.git goyaml
git clone --depth 1 --branch v1.11.0 https://github.com/uber-go/atomic.git uberatomic

# Дальше в go.mod проекта (в build-check копии):
cd /path/to/project
go mod edit -replace go.yaml.in/yaml/v3=/home/claude/vendor-src/goyaml
go mod edit -replace go.uber.org/atomic=/home/claude/vendor-src/uberatomic
```

⚠️ Важно: `--branch` при клонировании должен соответствовать версии из
`go.mod` (или ближайшей доступной ветке/тегу) — иначе рискуешь
подключить несовместимую версию API. Сверяй `go.mod` склонированного
репозитория (`cat go.mod` внутри) — module path там должен буквально
совпадать со строкой, которую заменяешь (`go.yaml.in/yaml/v3`, а не
что-то другое) — иначе `replace` не сработает.

Если версия в теге репозитория использует другую схему версионирования
(например, GitHub-зеркало не имеет тега `v3.0.4`, а только `v3`/`master`) —
не пытайся подогнать версию через `go mod edit -replace module=path@version`,
это часто ломается на "should be v0 or v1, not v3" и подобных ошибках.
Правильный путь — `replace module => /локальный/путь` (без `@version`) —
тогда Go берёт версию прямо из содержимого папки, минуя проверку тегов.

## Шаг 6 — финальная сборка

```bash
cd /path/to/project   # build-check копия, НЕ оригинал рабочей копии!
GOTOOLCHAIN=local GOPROXY=direct GOSUMDB=off go build ./...
GOTOOLCHAIN=local GOPROXY=direct GOSUMDB=off go vet ./...
```

Пустой вывод от `go build` = успех (в Go так принято: нет вывода — нет
ошибок). Любая ошибка компиляции покажет точный файл, строку и что
не так — этим и отличается реальная проверка от вычитывания кода
глазами.

## Рекомендуемая организация рабочих директорий

Чтобы не путать "то, что показываю человеку" с "тем, что нужно для
обхода firewall песочницы":

```
/home/claude/work/<service>/       — чистая рабочая копия, БЕЗ replace-хаков.
                                      Именно отсюда берутся файлы, которые
                                      показываются человеку через cat > file.
/home/claude/buildcheck/<service>/ — копия ТОЛЬКО для проверки сборки,
                                      с изменённым go.mod (replace-директивы,
                                      возможно пониженная версия go).
                                      Синхронизируется из work/ перед каждой
                                      проверкой:
                                      rsync -a --exclude='go.mod' work/X/ buildcheck/X/
/home/claude/vendor-src/           — склонированные зависимости для replace,
                                      общие для всех сервисов проекта.
```

Скрипт-обёртка для повторной проверки (сохрани один раз, вызывай на
каждом шаге):

```bash
cat > /home/claude/buildcheck/verify.sh << 'EOF'
#!/bin/bash
set -e
cd "$(dirname "$0")/<service>"
echo "=== go build ./... ==="
GOTOOLCHAIN=local GOPROXY=direct GOSUMDB=off go build ./...
echo "=== go vet ./... ==="
GOTOOLCHAIN=local GOPROXY=direct GOSUMDB=off go vet ./...
echo "=== OK: сборка и vet прошли чисто ==="
EOF
chmod +x /home/claude/buildcheck/verify.sh
```

## Бонус: реальный (не только компиляционный) прогон кода

Раз Go в песочнице реально работает — можно не только собирать, но и
**запускать** программу и смотреть на её настоящий вывод. Это особенно
полезно для проверки конфигов, парсеров, чистой логики без сетевых
вызовов (сетевые вызовы к внешним хостам типа Gate.io в песочнице не
пройдут — allowlist это заблокирует, см. следующий раздел).

Пример (как проверяли `config.Load()` в market-data):

```bash
# Временно копируем тестовую программу в cmd/ существующего модуля
# (пакеты internal/* доступны для импорта только внутри своего модуля)
mkdir -p buildcheck/<service>/cmd/selftest
cat > buildcheck/<service>/cmd/selftest/main.go << 'EOF'
package main
import (
    "fmt"
    "log"
    "github.com/<org>/<repo>/<service>/internal/config"
)
func main() {
    cfg, err := config.Load("config.yaml")
    if err != nil {
        log.Fatalf("Load failed: %v", err)
    }
    fmt.Printf("%+v\n", cfg)
}
EOF

cd buildcheck/<service>
GOTOOLCHAIN=local GOPROXY=direct GOSUMDB=off go build -o /tmp/selftest_bin ./cmd/selftest
cd /tmp && mkdir -p selftest_run && cp /path/to/test-config.yaml selftest_run/config.yaml
cd selftest_run && /tmp/selftest_bin

# Уборка за собой после проверки:
rm -rf buildcheck/<service>/cmd/selftest /tmp/selftest_bin /tmp/selftest_run
```

## Ограничение, которое НЕ решается никакими трюками

Песочница Claude **не может** реально подключиться к внешним сервисам
вне allowlist (Gate.io, реальный Redis на VDS и т.д.) — только к
`github.com`, `pypi.org`, `npmjs.com`, `archive.ubuntu.com` и
подобным пакетным реестрам. Поэтому:

- **Компиляция, статический анализ, юнит-тесты на чистой логике** —
  можно и нужно проверять в песочнице до показа человеку.
- **Реальное сетевое взаимодействие** (подключение к бирже, к
  боевому/pre-prod Redis, живой прогон `go run` торгового процесса) —
  ВСЕГДА остаётся на стороне человека, на его локалке или VDS.
  Не пытайся имитировать это как "то же самое, что реальный прогон" —
  это разные уровни проверки, и оба нужны, но по-разному.
